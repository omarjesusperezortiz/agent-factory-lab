Orchestrator design · why tickets go missing

    
Ticket Orchestration Flow

    
Today an LLM keeps track of which tickets to run, and some get lost. The fix moves the bookkeeping into code: a ledger holds every ticket, code starts one run per row, and a final check compares assigned with finished. LLMs do the work inside each run, and an optional triage LLM looks only at the failures.

  


  

    

    
  


  

  

    
Which piece catches which failure

    

      
What goes wrong todayWhat catches it

      
        
The LLM skips or forgets a ticketCode loops over the ledger. The LLM never decides which tickets run.

        
Only the first page of tickets is fetchedFetch every page into the ledger before any run starts. Reconcile also flags it.

        
A worker crashes and the ticket vanishesIts row stays at building, and the sweeper re-queues it after 30 minutes.

        
The batch restarts halfwayThe ledger and LangGraph's checkpointer keep state, so the batch resumes instead of starting over.

        
A ticket keeps failingThe reconcile step reports it, the triage LLM reads why, and it retries, re-specs or alerts you.

Agent Harness Playbook

    
How to set up the runtime around each agent in a spec → build → test → review workflow: what each stage reads, what it may touch, where retrieval helps, how work gets checked, and how you tell whether a change made things better. Token counts and timings are illustrative.

    

      HandoffsPermissionsContext & RAG
      ChecksEvalsAvoidWhere to start
    

  


  
  

    
Pass outputs between stages, not the conversation

    
When every stage reads the whole history, context grows at each step and an early mistake travels all the way to review. Give each stage only the previous stage's output plus what it needs to look up itself.

    
  


  
  

    
Give each role only the tools it needs

    
Each ticket gets its own git worktree or container and its own branch, so tickets can run in parallel without touching each other. Inside it, permissions follow the role. A tester that can't edit source can't make a failing test pass by changing it.

    

      
RoleRead codeEdit filesRun commandsNetworkLimits

      
        
Scoutyesnosearch onlydocs index15 min · 60k tokens

        
Workeryesown worktreebuild, formatno30 min · 150k tokens

        
Testeryestest files onlytests, lint, typecheckno20 min · 3 rounds

        
Revieweryesnonono10 min · 60k tokens

      
    

    
Every limit fails loudly and writes failed to the ledger. Make every stage safe to re-run: running it twice should never open a second pull request or post a duplicate ticket comment. That is what lets the sweeper re-queue stuck tickets without side effects.

  


  
  

    
Search the code live, retrieve everything else

    
Code changes every commit, so an index of it goes stale and chunking splits functions apart. Agents that search and open files directly find the right code more reliably. Retrieval pays off for knowledge that lives outside the code and changes slowly.

    
  


  
  

    
Run cheap, exact checks before any LLM judgment

    
Order the checks from cheapest to most expensive and stop at the first failure. The reviewer should only see code that compiles and passes its tests, and it should never be the model that wrote the code.

    
  


  
  

    
Replay closed tickets before you ship a change

    
Without a fixed test set, every prompt or model change is a guess. Take 20 to 50 tickets you already closed, replay them whenever something changes, and compare against the last good run.

    
  


  
  

    
Patterns to avoid

    

      
AvoidDo instead

      
        
An LLM tracking which tickets to runA ledger in code, plus a reconcile check at the end of each batch. See Ticket Orchestration Flow.

        
Agents chatting freely with each otherFixed handoffs with a defined output per stage.

        
One shared scratchpad every agent writes toEach stage writes its own file; the next stage reads it.

        
The worker grading its own codeA separate reviewer call with a skeptical prompt, possibly another model.

        
Approval gates on every stepApprove the spec. Approve merges only for risky tickets.

        
Fixing failures with longer promptsAdd a tool, a check or a narrower context, then confirm with a replay.

      
    

  


  
  

    
Where to start

    
    
      
  1. Ticket ledger and reconcile stepFixes tickets going missing. Everything else builds on knowing each ticket's status.
    2. 
      
  2. Worktree per ticket and permissions per roleMakes parallel runs safe and stops the tester from editing its way to green.
    3. 
      
  3. Deterministic checks before reviewTypecheck, lint and tests first. Cuts reviewer cost and catches most worker mistakes.
    4. 
      
  4. Replay set of 20 to 50 closed ticketsFrom here on, every change is measured instead of guessed.
    5. 
      
  5. Retrieval over past specs and PRsAdd it last, once the replay set can show whether it raises spec approval.

Who starts what

      
The orchestrator stays code. It starts one headless Claude Code process per stage (claude -p --agent <name>) inside the ticket's worktree, and a hook reports each result back to the ledger. Scheduled jobs sit around it.

      
    


    

      
The four building blocks

      

        
PieceWhat it isWho starts itLives inUse it for

        
          
SkillA folder with SKILL.md plus optional reference files and scripts. Custom commands have merged into skills: .claude/commands/x.md still works, but new work should be a skill.You with /name, or Claude when the description matches. disable-model-invocation: true makes it you-only..claude/skills/<name>/Repeatable procedures: write a spec, run checks, review a diff

          
SubagentA Markdown file whose body is the system prompt, with its own tools, model, turn limit and optional isolation: worktree.Claude delegates by description, you @-mention it, or claude --agent name runs a whole session as it..claude/agents/The roles: scout, worker, tester, reviewer

          
HookA command, HTTP call, MCP tool, prompt or agent that runs on a lifecycle event. Exit code 2 or a JSON decision blocks the action.Claude Code itself, on events like PreToolUse, PostToolUse, SubagentStop, Stopsettings.json, or a subagent's or skill's hooks fieldGuardrails that must always hold, formatting, reporting to the ledger

          
SettingsPermissions, hooks, model and MCP servers. Precedence: managed policy, then CLI flags, then local, project and user settings.Loaded at session start.claude/settings.json (committed), settings.local.json (gitignored)Rules that shouldn't depend on the model reading CLAUDE.md

        
      

      
Rule of thumb: CLAUDE.md and skills are advice the model reads; settings and hooks are enforced by the harness. Anything that must always hold, like "the tester never edits source", belongs in a hook or a permission, not a prompt.

Gotchas from the docs

      
    
        
  • Cloud scheduled tasks act as you and never ask permission. All your connectors are included by default, writes included. Remove every connector a task doesn't need.
    • 
        
  • A green run means the session ran, not that the work succeeded. Have every scheduled task write its outcome somewhere you check, like the ledger or a Slack post.
    • 
        
  • API fire text arrives as untrusted data. The task's saved prompt must say explicitly to act on the payload.
    • 
        
  • Minimum interval is one hour for cloud schedules. Anything more frequent belongs in your own cron or engine.
    • 
        
  • isolation: worktree branches from your default branch, not the parent session's HEAD, and is cleaned up only when the subagent made no changes.
    • 
        
  • A hook that crashes doesn't block by default. Set "onFailure": "block" on hooks that guard something important.
    • 
        
  • Skill descriptions drive auto-loading. Put the phrases people actually type in description, and keep SKILL.md under 500 lines with detail in reference files.

Research round 3 · retrieval and context · Oct 2026

      
RAG and context for coding agents

      
Which retrieval method fits which question, what the 2026 evidence says, and how long-running agents keep their context clean. Evidence labels show how much to trust each claim.

      
Question → methodEvidenceLong runsOur rollout

    


    

      
Pick the retrieval method by the question

      
"RAG or not" is the wrong question. Each kind of question has a method that fits it, and most coding questions are answered best by searching the live code.

      
    


    

      
What the evidence says

      

        
FindingStrengthSource

        
          
Claude Code started with a local vector database, then moved to agentic search because it worked better and avoided staleness, security and privacy issues.secondhand interviewMedium

          
Code has exact identifiers, call graphs and types that embeddings capture poorly; exact search and symbol lookup often win.blogDEV

          
A survey of repository-level code generation describes the shift from static embeddings to tools in a plan-act-observe loop.survey paperarXiv 2510.04905

          
Counterpoint: grep needs the right words, so conceptual questions may still need a semantic index. The debate is open.tracked debateGitHub

          
For documents, hybrid keyword + vector search with rank fusion and a reranker is the common default. Reranking showed no advantage in one benchmark, so test it on your own data.guides + benchmarkAtlan, ARAGOG

          
Graph RAG helps with relationship and theme-level questions; for "what did X say about Y", hybrid plus rerank is usually enough. Start simple and add pieces only when evals show a specific failure.guidesAtlan, Turing Post

        
      

    


    

      
Keeping long runs coherent

      
    
        
  • Load just in time. Keep file paths, ticket IDs and queries in context, and fetch the content when it's needed. Anthropic engineering post; secondary summaries
    • 
        
  • Write notes to disk. A progress file per ticket (what's done, what's next, open questions) survives compaction and restarts, and the next stage can read it. Anthropic engineering post
    • 
        
  • Tune compaction on real traces. Make sure the summary keeps everything important first, then trim. Several 2026 papers find agents compact early, well before the window is full, to avoid quality loss. Anthropic; arXiv
    • 
        
  • More context can make agents worse. A long, noisy window dilutes attention, which is another argument for passing stage outputs instead of transcripts. Morph; Anthropic
    • 
      

    


    

      
Our rollout

      
    
        
  1. AGENTS.md and agentic searchZero infrastructure. Covers exact lookups, which are most coding questions.
    2. 
        
  2. Per-ticket notes filespecs/<ticket>/notes.md, written by each stage. Handles long runs and restarts.
    3. 
        
  3. Knowledge index for historyClosed tickets with their specs and PRs, ADRs, incident write-ups. Hybrid search, re-indexed nightly. Measure spec approval before and after.
    4. 
        
  4. Semantic code index or code graph, only on evidenceAdd one when replay evals show misses on conceptual or dependency questions, not before.
    5. 
      

    

  


  
  

    

      
Research round 3 · people, oversight and shared setup · Oct 2026

      
Working as a team with supervised agents

      
How much autonomy each action gets, how to share skills and guardrails across a team, how to keep up with agent pull requests, and what to log. Mostly practitioner and vendor sources, plus a few papers and official docs.

      
Supervision ladderSharing the setupReviewing agent PRsSkills as team assetsAudit trail

    


    

      
Supervise by risk, not by stage

      
Approving every agent action doesn't scale, and regulators and safety researchers say so too. Sort actions into tiers by risk and reversibility, gate only the risky tiers, and loosen a gate only when the track record justifies it.

      
    


    

      
Sharing the setup across a team

      
    


    

      
Reviewing agent PRs without burning out

      
The bottleneck has moved from writing code to reviewing it. Don't lower the bar; shrink the unit of review and let automation take the first pass.

      

        
FindingStrengthSource

        
          
High-AI teams merge 98% more PRs, but review time rises 91%.cited study, unnamedOptinode

          
Agent PRs wait about 5.3× longer to be picked up than unassisted ones.vendor benchmarkCodacy citing LinearB

          
Many AI-authored PRs get no independent review; human involvement is often steering the agent rather than reviewing.paperarXiv 2610.11179

          
The risky AI PRs are the ones that look clean, not the obviously bad ones.practitioner, 100 PRsMedium

          
Anthropic's Claude Code team layers CI, AI review and human approval, and ownership continues after merge: author and on-call watch the change, with flags and fast reverts.secondhand summaryOptinode

        
      

      
    
        
  • Small PRs. One ticket, one PR; split large generated diffs. Factory, Atomic Robot
    • 
        
  • Every PR carries its evidence. Link the spec, the test report and the reviewer verdict from our pipeline in the description. Factory
    • 
        
  • Disclose and name an owner. Mark agent authorship and name the human accountable for each merge. AI Policy Desk
    • 
        
  • Route by risk. Changes touching auth, money or production access go to people who know those areas. Factory, KORE1
    • 
        
  • Review in short blocks of 25 to 30 minutes and hold occasional retros on rubber-stamping. Atomic Robot
    • 
        
  • Keep learning from diffs. Review used to be how engineers learned the system; ask the reviewer agent for a short explanation of each change. Optinode
    • 
      

    


    

      
Skills as team assets

      
    
        
  • Agent Skills is a cross-tool standard. Released by Anthropic in December 2025, with 40+ clients listed by September 2026, including Codex and GitHub Copilot. Skills you write work beyond Claude. Atlan; Paperclipped
    • 
        
  • No versioning standard yet. A SemVer proposal is under discussion, and one ecosystem study found most skills are never updated after release. Version your shared skills through the plugin marketplace. agentskills discussion #415; arXiv 2607.09065
    • 
        
  • Test skills with on/off comparisons. Run a frozen set of prompts with and without the skill and record the skill version in traces. Hand-testing misses regressions. MLflow; Future AGI; SkillTester
    • 
        
  • Skills are a supply chain. Several 2026 papers audit open skills for security issues. Review third-party skills like code before installing, and pin versions. arXiv 2603.00195; OpenSkillEval
    • 
      

    


    

      
What to log

      
Audit guidance converges on action-level evidence: what the agent accessed, what it did, and under whose authority, not only the final output. Our pipeline already produces most of it.

      

        
Question an auditor asksWhere we answer it

        
          
What did the agent read and run?OpenTelemetry trace per ticket, one span per tool call

          
What did it change?Branch and PR per ticket, diff linked from the ledger

          
Who approved it?Spec approval and merge approval recorded in the ledger with the approver

Research round 5 · spec-driven development · Oct 2026

      
Spec-driven development, step by step

      
An agent guesses wherever our intent was never written down, and each guess branches. A spec is a persistent file that records those decisions before code exists, and checks the code against them afterwards. Built around OpenSpec, compared with the other frameworks, and mapped onto our ticket pipeline.

      
The loopDelta specsOur pipelineFrameworksRisksVideos

    


    

      
The loop: explore → propose → apply → verify → archive

      
Press play, or click a step. The example is the one from the OpenSpec intro video: adding remember-me to a login.

      

        

        
      

      

        

        

        
AGENT

        

        

      

      

    


    

      
Delta specs: a change only describes what changes

      
This is what makes OpenSpec work on existing code. A change folder holds only ADDED / MODIFIED / REMOVED requirements. Archiving merges them into openspec/specs/, which stays the up-to-date description of the system.

      

      

      
Format from the OpenSpec docs: ### Requirement: with SHALL/MUST (RFC 2119), #### Scenario: with GIVEN/WHEN/THEN. Each scenario is meant to become one test.

    


    

      
Our pipeline already is this loop

      
Our orchestrator → scout/spec → human approval → worker → tester → review is the same shape as OpenSpec, and almost exactly the harness BettaTech built (leader, spec author, implementer, reviewer, human gate). What we lack is a shared file format and an archive step.

  1. Adopt the file format, keep our orchestratorOur ledger and sweeper still own the ticket list. OpenSpec only defines what the scout writes and the reviewer checks.
    2. 
        
  2. Add an sdd flag per ticketBettaTech marks each task sdd: true/false. Typos and one-line fixes skip the spec stage; everything else goes through it.
    3. 
        
  3. Put project rules in openspec/config.yamlStack, conventions and "no tests for X" go there once, so explore stops asking the same questions every ticket.
    4. 
        
  4. Make the reviewer read the spec, not the chatEach stage gets only the files: no conversation history crosses a stage boundary.
    5. 
        
  5. Archive on mergeThe sweeper runs archive when the PR merges, so specs/ never drifts from what shipped.
    6.

Risks and how to avoid them

      
    
        
  • Waterfall again. Critics (Marmelab, and per secondhand reports Beck and Fowler) warn against writing everything up front. Fix: specs change while you build; freeze nothing.
    • 
        
  • Too much markdown. Lackner and Augment both say long specs get rubber-stamped and give worse results. Fix: bullets, short paragraphs, review time under 10 minutes.
    • 
        
  • Not every task needs one. Quick or exploratory work is faster with one prompt. Fix: the sdd flag.
    • 
        
  • Drift. Specs that nobody updates are worse than none. Fix: archive on merge, and verify against the spec before review.
    • 
        
  • Approving without reading. "Many people just click accept, but the value is in the review" (Augment). Fix: a human approves spec_ready, and the approver is recorded in the ledger.

Research round 6 · orchestration options · Oct 2026

      
Ways to orchestrate a software factory

      
From "you watch panes in herdr" to "a durable workflow engine runs the agents". Nine ways, the jobs a factory needs done, and which of those jobs each one actually covers. Click a row, then run a ticket through it and see what happens when the worker crashes: the "missed ticket" problem.

Nine ways, six jobs

      
A factory needs six jobs done: a ticket ledger (source of truth), a dispatch loop (who starts the next agent), isolation (worktree or sandbox per ticket), recovery (what happens on a crash), human gates, and visibility. No single tool does all six well. covers it partly not at all, or you build it

      

        
WayLedgerLoopIsolationRecoveryGatesVisibilityAgents

When to move up a level

      
Each level fixes a pain the previous one has. Move up only when you feel that pain; every level adds setup and cost.

      
    
        
  1. Panes: herdr or Claude Squad plus git worktreesOne person, 2–5 agents. You are the orchestrator. herdr tells you which pane is blocked, working or done. Pain that pushes you up: you forget a pane, so tickets get missed.
    2. 
        
  2. A ledger in code, with agents run headlessThe tracker is the source of truth. A small loop polls it, starts claude -p (or the Agent SDK) in a worktree per ticket, and a sweeper re-queues stale rows. This is the Symphony and Baton pattern. Pain that pushes you up: long runs die mid-way and restarting from zero is expensive.
    3. 
        
  3. A durable engine: Temporal, or LangGraph with a checkpointerEach stage becomes an activity or node that retries and resumes on its own. Human gates become signals or interrupt(). Pain that pushes you up: the laptop or server becomes the bottleneck.
    4. 
        
  4. Cloud sandboxes: Claude Managed Agents, or hosted issue→PR agentsEach session gets its own sandbox. The dispatch loop stays yours. Gas Town shows the extreme case: about 100 agents and 50 PRs a day, at about a billion tokens a day.
    5. 
      

    


    

      
Recommended stack for our pipeline

      
Mix and match by job. The part that stops tickets going missing, the ledger and the dispatch loop, stays in plain code, never inside a chat session.

      

        
JobUseWhy

        
          
LedgerLinear or GitHub issues; states pending → spec_ready → in_progress → testing → review → doneHumans can already read it. Symphony and Baton both use the tracker as the state machine.

          
LoopOur poll → dispatch → reconcile, plus the sweeperThis is the fix for missed tickets. Move it into Temporal only when crashes hurt.

          
IsolationOne git worktree per ticketEvery orchestrator surveyed does this. It prevents two agents editing the same files.

          
Agentsclaude -p or the Agent SDK, one call per stage. Use subagents inside a stage, for example three reviewer lenses.Only files pass between stages, never chat history (see the Spec-driven tab).

          
WatchingherdrFor the sessions a person drives (spec review, debugging). It shows blocked, working and done at a glance.

          
GatesThe spec_ready state and the mergeTwo human gates, both visible in the tracker.

          
VisibilityOpenTelemetry traces, one per ticketSee the OpenTelemetry tab.

        
      

      
    
        
  1. Don't build the factory on agent teamsAgent teams are experimental and need an interactive session. /resume doesn't bring in-process teammates back, and the docs say task status can lag and block dependent tasks. That is the missed-ticket problem again. They are good for research and review swarms.
    2. 
        
  2. Borrow from Gas Town, don't install itThe ideas worth taking: one supervisor and many disposable workers, a merge queue (its "refinery"), and a health watcher (its "witness"). The toolkit itself is alpha, takes a day to set up and burns tokens fast.
    3. 
        
  3. Read Symphony's WORKFLOW.md before writing our ownIt is a small reference implementation of exactly our loop: poll the board, one workspace per ticket, restart stalled agents. OpenAI does not maintain it as a product.

Research round 8 · prompting for outcomes · Oct 2026

      
Be more ambitious with the agent

      
The same model gives some people remarkable results and others ordinary ones, because it does exactly what it's asked. Felix Rieseberg (who led engineering on Claude's apps) splits "ask for more" into four kinds: speed, altitude, depth, range. Then he adds two things that make them work: an outside judge, and real resources. Built from his essay and AI Labs' video walkthrough, using the video's example: a hiring app.

      
The ladderOur pipelineWhen not toSources

    


    

      
One task, asked six ways

      
Press play, or click a scene. Each one is redrawn from the motion graphics in the video. The kinds stack: each step keeps the previous ones.

      

        

        
      

      

      

    


    

      
Where each one plugs into our pipeline

      
None of these needs a new tool. They change what each stage is asked for, and most can be written into the stage prompts once.

      

        
KindThe questionStageConcrete change

        
          
AltitudeWhat's the goal behind the goal?Ticket intake / orchestratorEvery ticket gets an outcome field ("roles fill faster") next to the task ("add a dashboard"). The scout plans against the outcome.

          
DepthWhat would the best practitioner do?Scout / specBefore writing proposal.md, the scout answers the four depth questions. Answer 4, "what proves it", becomes the scenarios in the spec.

          
JudgeWho checks, other than the builder?Tester, reviewerThe reviewer runs on a different model (codex exec, or a fresh claude -p with only the files). Prefer judges the agent can run: tests, measurements, a reproduction.

          
RangeWhich other fields would see this differently?Final reviewDescribe the product as a verb, then a sequence of specialist subagents, each with a method, not a persona, and a red team at the end. Only for big tickets: it is slow.

          
ResourcesCan it see, understand and test the problem?Worker environmentMCP to the error tracker, a version → commit map, and a sandbox where the worker can reproduce the bug and prove the fix.

        
      

      
    
        
  1. Add outcome to the ledger rowThe cheapest change with the biggest effect. Without it, every downstream stage optimises for "task done".
    2. 
        
  2. Depth questions in the scout promptThis fits OpenSpec's explore step: "what a professional would do that I'm not asking for" is exactly the question explore should ask.
    3. 
        
  3. A different model for the reviewerWe already separate tester and reviewer. Making the reviewer a different model is a one-line change in the dispatch loop.
    4. 
        
  4. Range as a label, not a defaultA range label on the ticket triggers the specialist sequence. Default tickets skip it, because it takes a long time.
    5. 
      

    


    

      
When not to

      

        
KindBreaks when

        
          
SpeedIt scales whatever you already do, mistakes included.

          
AltitudeThe work is creative, with no single right result, or the agent can't reach the data and permissions the outcome needs.

          
DepthThe work is throwaway, because depth costs much more compute. Without a judge, "expert standard" is just a claim.

          
RangeIt becomes role-play. "Write like a recruiter" changes the tone, not the work. Remove any specialist that has no concrete method or tool.

          
Outside judgeThere's nothing to run. Content is harder to judge than code; asking for citations helps, but it is not independent.

          
All of themRieseberg: "There are currently limits." "Claude, go make money" still doesn't work on its own.

Round 2 · orchestration internals

      
Five more searches on running a spec → build → test → review pipeline in production. Mostly practitioner blogs and vendor comparisons, plus a few research papers. What it changes for us is in bold.


      

        
Durable execution engines

        
          
FindingTemporal, Restate, Inngest, DBOS, Vercel Workflow and LangGraph's checkpointer all give retries, resume after a crash and long human waits. Temporal is treated as the mature default and shipped an OpenAI Agents SDK integration in April 2026. DBOS fits teams already on Postgres. Restate and Inngest are source-available, not OSI open source.

          
Known pitfallLarge LLM payloads fill up workflow history. Inngest bills per step, so retries and multi-model calls add up.

          
For usThe ledger plus sweeper we designed is a hand-built version of this. Pick an engine instead of writing it: the human spec approval becomes a signal or awaited event, and the sweeper becomes built-in retries. Store spec, diff and test report as files and pass references, not contents, through the engine.

        
      


      

        
Spec-driven development

        
          
FindingEvery major coding tool now ships a spec workflow. GitHub Spec Kit runs constitution → specify → clarify → plan → tasks → implement, writing a markdown file at each step. Kiro produces requirements, design and a task list. Critics call it "waterfall 2.0" when specs get heavy.

          
For usYour scout/spec stage is this pattern. Borrow two pieces: a clarify step, where the scout lists open questions before you approve, and a constitution, the project rules every spec must respect (your AGENTS.md). Keep specs to one page so approval stays fast.

        
      


      

        
Multi-agent coding pipelines

        
          
FindingPractitioners and one arXiv paper found file-based handoffs work better than agents messaging each other. The tester should write and run tests but not fix code; one author says false positives disappeared after that split. Use a different model to review than to write. A research pipeline caps revision loops at 3 rounds. A figure attributed to Anthropic, which we couldn't verify, puts multi-agent systems at about 15× the tokens of chat.

          
For usConfirms the playbook: output handoffs, a tester that can't edit source, a separate reviewer and loops capped at 3. Expect real token cost, so track cost per ticket from day one.

        
      


      

        
Claude Code: subagents, agent teams, worktrees

        
          
FindingSubagents delegate one way and share no state. Agent teams add peer messaging and a shared task list, but are described as experimental and about 7× the tokens of a normal session. isolation: worktree in a subagent's frontmatter gives it its own worktree. Guides report 4 to 8 parallel worktrees per developer. One note says /resume doesn't restore teammates. These come from third-party guides, so check them against Anthropic's docs.

          
For usUse subagents with worktree isolation, one per ticket, started by code. Skip agent teams for ticket batches. The resume gap is one more reason the ledger must live outside the agent session.

        
      


      

        
Evaluating on your own tickets

        
          
FindingPublic SWE-bench is treated as a floor. Private replay of your own last ~50 merged PRs is the strongest signal, with tasks held out, fixed budgets, and scoring of the whole run rather than only the final diff. Final-state-only checks let many broken solutions pass in one benchmark study. SWE-Together adds scenarios where the user corrects the agent mid-task.

          
For usBuild the replay set from closed tickets with their merged PRs. Score each stage (spec approved, first-pass tests, review verdict, cost), and include tickets where you rejected the first spec, so the clarify and rewrite path gets tested too.

OpenTelemetry
The open standard that lets one agent trace show up in any of these dashboards.

    

      
OpenTelemetry (OTel) is an open-source, vendor-neutral standard for telemetry: traces, metrics and logs. It is a CNCF project with SDKs for Python, JS, Go, Java and more. Your code records what happened. An exporter ships that data over the OTLP protocol to whichever backend you pick. If you switch vendors, you change the exporter and leave your code alone.

      
For agents, the useful part is tracing. One run of the graph is a trace. Every node, model call and tool call inside it is a span with a start time, a duration, a parent and attributes. The GenAI semantic conventions standardize attribute names such as gen_ai.request.model and gen_ai.usage.input_tokens, so Langfuse, Phoenix, LangSmith or Datadog can all read cost and token usage the same way.

    

    

      
How data flows

      

        
Your agentLangGraph + OTel SDK, or auto-instrumentation (OpenLLMetry, OpenInference)

        
→

        
OTLP exportSpans batched over gRPC or HTTP

        
→

        
Collector Optional. Sampling, PII redaction, fan-out to several backends

        
→

        
BackendLangfuse · Phoenix · LangSmith · Jaeger · Datadog · Grafana Tempo

      

    

    

      

        
Minimal Python span

        
from opentelemetry import trace

tracer = trace.get_tracer("refund_agent")

def researcher(state):
    with tracer.start_as_current_span("chat claude-sonnet-5-5") as span:
        span.set_attribute("gen_ai.operation.name", "chat")
        span.set_attribute("gen_ai.request.model", "claude-sonnet-5-5")
        resp = llm.invoke(state["messages"])
        usage = resp.usage_metadata
        span.set_attribute("gen_ai.usage.input_tokens", usage["input_tokens"])
        span.set_attribute("gen_ai.usage.output_tokens", usage["output_tokens"])
        return {"messages": [resp]}

      

      

        
Glossary

        

          
trace
One end-to-end run, such as a full graph invocation.

          
span
One timed step inside a trace. Spans nest into a tree.

          
attribute
A key/value fact on a span: model, tokens, tool name.

          
exporter
Sends spans out of your process, usually over OTLP.
