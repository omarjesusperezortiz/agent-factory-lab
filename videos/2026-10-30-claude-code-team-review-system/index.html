How the Claude Code team checks what agents build

Agents write a lot of code and call the task done, then you find what they missed. AI LABS walks through the review system the Claude Code team described and turns it into a workflow you can copy: evals written first, a separate reviewer, a bounded build-review loop, rules that stick, risk-based strictness, and a fast way to find and undo mistakes. The team reports more than twice as many changes shipped, with the share they had to undo down by over 40%. The running example is one feature moving through every step.

What this means for us

Pattern from the videoHow to apply it
Evals written and approved before any buildFor each feature, write the requirements and a strict eval file first, and have a human approve both. Add a hook that blocks "done" until the evals pass. This is the "Evals" tab of the console, with the Human inbox as the approval step.
The builder never grades its own workRun build, verify and review as separate sub-agents with fresh context windows, with the main agent only orchestrating. Keep a state.md that records the round and what is still failing.
review.md, linked from CLAUDE.mdPut what counts as a failure, severity, what to ignore and how to report in one file. The video says Claude doesn't read it by default, so link it from CLAUDE.md so every session loads it.
A "rules learned" section with a human gateWhen the same problem shows up in a later round, or review keeps flagging a non-problem, propose a one-line rule. Add it only after approval. This is how the factory stops repeating itself across sessions.
Risk tier decides strictnessAsk "what happens to a customer if this breaks?" Low = looks wrong, medium = feature stops but nobody loses anything, high = money, lockout or someone else's data. Pass the tier to the eval step, so high-risk features get the strictest evals.
Cap the rounds, stop on repeatsTheir rule is a rethink after 3 rounds, re-reviewing only what the last fix changed, and tagging each problem by kind. AI LABS stops its own loop at 5 rounds (each does more) or when the same problem survives 2 rounds of fixes. Pick numbers by cost per round.
Fresh first-time-user agent, plus branch per featureAfter the evals pass, send an agent with no access to the code to use the live app on a temporary database. Keep one git branch per feature and a commit for every working version, so a bad change can be found and rolled back quickly.
