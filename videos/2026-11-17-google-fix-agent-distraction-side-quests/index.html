Side quests: why agents drift off task, and how Google cleaned up what distracts them

An agent reads every old plan, stale note and outdated rule in your project and treats each one as something to act on. Google calls the result side quests. It measured them across its own engineers' sessions, then built agents that find stale notes and prove they're stale before removing them. AI LABS rebuilt the idea for Claude Code: two CLAUDE.md rules, status tags on tickets, and a /sweep skill. Running example: a demo shop app whose login ticket still says "email or Google" after the team dropped Google.

What this means for us

IdeaWhat to do in the factory
The code is the source of truthPut the rule in every builder's CLAUDE.md: when notes, plans or instructions disagree with the app, follow the app and say so in the reply. The one exception is a ticket marked in progress, where the plan wins over half-built code.
Every ticket carries a statusnot started / in progress / done / dropped in each rd.md. A feature that's in the plan but missing from the code is only a gap if its status says so. Builders set it to done when they finish.
List side quests, don't take themBuilders leave TODOs, notes and plans they weren't asked about alone and list the relevant ones at the end of the reply. Those lists can feed the Issues view, so nothing gets fixed quietly.
Changes to a plan go through the planWhen a request conflicts with a spec (like "email only"), the agent stops and asks before building. Then the spec gets updated in the same session, not three sessions later.
Sweep on a schedule, delete only with proofRun a read-only sweep: verifiers get the claims only, check them against the code and git history, and return CURRENT / OUTDATED / UNPROVEN. Conflicts go to the Human inbox. Approved files move to archive/, and a hook blocks agents from reading it. Claude Code's loop and monitor stop when the session closes, so a weekly sweep needs a scheduler (launchd or a cloud routine).
One task, one sessionStart a new session per ticket, even right after planning, so failed attempts don't stay in context. Watch for side quests on the Traces view: extra actions and tokens on a run that still "passed".
